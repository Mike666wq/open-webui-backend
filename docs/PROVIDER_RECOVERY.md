# 服务商接入故障恢复手册

> 本文对应规划件 **P-001 r2**。目标是让「连接失败」能被定位到**真实阶段与真实原因**，
> 并给出一条**可回滚**的恢复路径。
>
> 本文只交付**脱敏诊断方法**与**运维步骤**。生产环境的具体变更由**部署责任人**执行；
> 执行者不改生产容器、代理配置，也不重启服务。

---

## 1. 先分清三类连接

| 类型                       | 存在哪里                  | 谁能改                        | 备注                                 |
| -------------------------- | ------------------------- | ----------------------------- | ------------------------------------ |
| **服务器托管的服务商连接** | 服务端连接表 + 快照       | 连接所有者；共享连接的管理员  | 本文与错误分类针对的就是这一类       |
| **旧 OpenAI 连接**         | 旧配置里的 `OPENAI_API_*` | 管理员（迁移预览 → 明确确认） | 迁移保留 Key、模型名与访问规则       |
| **浏览器直连**             | 用户浏览器的 localStorage | 用户自己                      | 由浏览器发起，不在服务端，不参与迁移 |

判断依据与入口见 `docs/provider-connections.md`；接口字段见 `docs/PROVIDER_CONTRACT.md`。

---

## 2. 错误对象：阶段、原因、建议动作

错误对象除了五类 `category`，还带三个**可选**字段：

| 字段               | 取值范围                                                                                                                                                                                                   | 用途             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `stage`            | `catalog` / `oauth_refresh` / `inference`                                                                                                                                                                  | 失败发生在哪一步 |
| `reason`           | `invalid_credentials` / `token_expired` / `insufficient_permissions` / `rate_limited` / `quota_exhausted` / `address_blocked` / `dns_failure` / `tls_failure` / `timeout` / `upstream_failure` / `unknown` | 为什么失败       |
| `suggested_action` | `reconnect` / `replace_key` / `check_permissions` / `check_server_network` / `retry_later` / `inspect_connection`                                                                                          | 运维下一步       |

读法：

- `stage=catalog` + `reason=address_blocked` = **本站到厂商的这段路被拦了**，与凭据无关。
- `stage=oauth_refresh` + `reason=token_expired` = **登录态失效**，需要重新登录，不该去换 Key。
- `stage=catalog` + `reason=insufficient_permissions` = **账号权限不够**，换 Key 解决不了。
- `reason=unknown` = 证据不足，**不要**当成凭据失效处理。

三条硬规矩：

1. 只有真的刷新或鉴权证据才能说「凭据不可用」；
2. 目录失败**不能**证明推理不可用：目录与推理是两个独立阶段；
3. `upstream_status` 为空表示**没有上游响应**，是本地拦截或本地网络问题。

## 3. 恢复路线（fake-ip / 保留网段拦截）

典型现象：`获取模型列表` 报 `provider_network`，`hint` 里写明某个域名被解析到 `198.18.x.x`
（RFC 2544 保留段，常见于代理的 fake-ip）。

### 3.0 先取证（在**后端实际运行的网络命名空间**里做）

宿主机能连通**不等于**容器能连通。每一步单独记录结果。

```sh
# 1. 容器/进程实际使用的 DNS 是什么
cat /etc/resolv.conf
getent hosts api.siliconflow.cn        # 或 nslookup / dig，看解析到的地址

# 2. 直连一个上游 IP，确认出网本身是否通
curl -sS -o /dev/null -w '%{http_code}\n' --resolve api.siliconflow.cn:443:<真实IP> https://api.siliconflow.cn/v1/models

# 3. 代理是否接管了这段流量（TUN / redir-host / 透明代理）
ip -br addr | grep -E 'Meta|tun|utun'
ss -lntp | grep -E 'clash|mihomo|sing-box|redsocks'
```

#### 3.0.1 判定「DNS 是不是被代理的 fake-ip 劫持了」

**特征**：无论问哪个解析器，得到的都是 `198.18.0.x`（RFC 2544 基准保留段，Clash/mihomo 的 fake-ip 池）。
连 `223.5.5.5` 这种公共 DNS 也是 fake-ip，就说明请求根本没出机器——被本机的 TUN `dns-hijack` 截了。

```sh
# 分层问：主机与容器里都问一遍，结果一致 = 被劫持
for s in 127.0.0.53 223.5.5.5 119.29.29.29; do dig +short +tries=1 @$s api.siliconflow.cn; done
docker exec <容器> getent hosts api.siliconflow.cn
```

确认劫持源（mihomo）：

```sh
grep -A6 -E '^tun:|^dns:' <mihomo 配置> | grep -E 'dns-hijack|enhanced-mode|fake-ip-range'
#   dns-hijack: [any:53]        → 劫持所有接口的 53 端口，容器内网逃不掉
#   enhanced-mode: fake-ip      → 回 AAAA/A 假地址
#   fake-ip-range: 198.18.0.1/16 → 池子范围，决定 3.2 该放行哪一段
```

> 注意 `dns-hijack: any:53` 的影响面：它拦的是**这台机器上所有 DNS**，Docker 容器经
> `127.0.0.11` 转发到主机的查询同样会被劫持。所以宿主机 `dig` 看到真实 IP、容器看到
> fake-ip（或反过来）都是可能的，**必须在容器里再验一次**。

### 3.1 路线一（优先）：修代理 DNS 与出网

- 前提：代理确实接管了这段流量，但它把域名解析成了 fake-ip 地址。
- 做法：把代理的 DNS 模式从 `fake-ip` 改成 `redir-host`（或让域名解析返回真实地址），
  并确认后端容器的 DNS 指向能被真实解析的解析器。
- 配置范围：代理自身的配置文件 + 容器/主机的 DNS 配置。
- **改哪一份文件**：以代理客户端的**权威配置源**为准，不要改运行时生成的那份——
  客户端会在重新生成配置时覆盖它。以 Clash Verge 为例：`profiles/` 下的
  merge 增强模板（`type: merge`）与 rules 增强模板（`type: rules`）是权威源，
  GUI 的内存态文件会被回写抹掉。
- **热重载而不是重启进程**：TUN 模式下重启核心会让 DNS 短暂中断甚至不自启；
  先用 `mihomo -t -f <配置>` 校验，再通过控制 API 热重载，核心进程与 TUN 网卡都不落地。
- 验证：重跑 3.0 的 `getent hosts`，确认不再落到 fake-ip 段；然后在连接详情里重新获取模型列表。
- 回滚：恢复代理原 DNS 模式与原 DNS 配置。

### 3.2 路线二：显式放行该网段

- 前提：**已确认**该网段由可信代理接管，且代理能正确转发这些地址。
- 做法：显式设置环境变量

  ```sh
  # 网段取自代理的 fake-ip-range，按实际池子收紧，不要图省事写成 /15
  PROVIDER_ALLOWED_IP_RANGES=198.18.0.0/16
  ```

  然后**按本部署实际的方式**重建或重启后端（容器编排 / systemd / 手工进程，不要假设固定路径）。

- 配置范围：只放行这一个网段；回环、私网其它段、链路本地与云元数据地址**仍然拒绝**；
  TLS 校验与禁止重定向的行为**不变**。
- 验证：重新获取模型列表；确认放行的地址能进入连接流程，同时回环地址仍然被拒。
- 回滚：去掉该环境变量，按同样方式重启后端。
- **局限**：这条路只解除**本站**的拦截。代理是否真能把这批地址转发出去、
  选中的节点能否到达该厂商，**由 3.4 单独判定**。

### 3.3 两条路线的共同声明

- 放行网段**只**解除本站的本地拦截，**不**保证代理接管、**不**保证登录成功、**不**保证模型调用成功。
- 代理接管与否只能由部署责任人在**实际运行的网络命名空间**里取证，不能由宿主机连通性代替。
- 当前出站使用 `trust_env=False`：**只**设置 `HTTP_PROXY` / `HTTPS_PROXY` **不**构成可用代理。
  若部署只能靠新增显式代理配置才能恢复，需要按升级件处理（方案 A：调整现有网络/可信网段；
  方案 B：新增带 SSRF 与代理路由约束的显式代理契约），**不得**静默开启全局环境代理。
- 还要确认代理**是否真的暴露了代理端口**：TUN 模式下核心常常只监听控制端口
  （`ss -lntp | grep mihomo`），此时「改用 HTTP 代理接入」根本无从谈起。

### 3.4 节点可用性：DNS 修好之后还可能卡在这里（独立于 3.0–3.3）

fake-ip 拦截只是第一层。**即使 DNS 已改成真实 IP，选中的代理节点仍可能根本连不上某个厂商。**
典型表现：域名解析正常、`curl` 到真实 IP 也连得上，但 TLS 握手被重置（`SSL_ERROR_SYSCALL`）
或直到超时——这是**出口节点**的问题，不是应用的问题。

判定（以 mihomo 为例，用它自己的探测接口逐节点测，比逐个 `ping` 靠谱）：

```sh
# 代理组下每个节点到目标 URL 的延迟；超时的节点不会出现在结果里
curl --unix-socket <mihomo 控制 socket> -H "Authorization: Bearer <secret>" \
  "http://localhost/group/<组名>/delay?url=https%3A%2F%2Fapi.openai.com%2Fv1%2Fmodels&timeout=8000"
```

要点：

- **逐个目标分别测**。不同厂商可能只有不同的节点能通，**未必存在一个节点通吃所有目标**。
- 有些地区线对某些服务直接不通（例如 OpenAI 不服务香港，香港节点测 ChatGPT 会超时），
  别只看延迟数字，要看该节点**在不在结果里**。
- 找到可用节点后，用**按域名的规则**把它们分流出去，而不是改全局选择——
  这样不影响用户其它流量。注意规则模板里直接写节点全名容易拼错，
  应当从生效配置里抄写全名。

## 4. 认证类失败怎么恢复

| 场景                      | 原因                               | 动作                | 怎么恢复                                                     |
| ------------------------- | ---------------------------------- | ------------------- | ------------------------------------------------------------ |
| ChatGPT / Kimi 登录态失效 | `token_expired`                    | `reconnect`         | 在连接详情里「重新登录」；**沿用原连接**，不会新建第二个连接 |
| API Key 被拒              | `invalid_credentials`              | `replace_key`       | 在连接详情里「更换 API Key」                                 |
| 账号缺少某模型/接口权限   | `insufficient_permissions`         | `check_permissions` | 检查该账号的套餐与模型范围；**换 Key 无效**                  |
| 限流 / 额度不足           | `rate_limited` / `quota_exhausted` | `retry_later`       | 等待或检查账户套餐与余额                                     |

恢复动作**不得**动的东西（回归测试已锁住）：

- 已勾选的白名单、模型改名、用途、启停状态、`connection_id:upstream_id` 稳定 ID；
- 分享范围与访问检查；
- 历史聊天里对这些模型的引用。

重新登录成功会**自动清除**该连接上与旧凭据相关的目录错误（目录快照指纹含凭据）；
取消、失败、超时与迟到响应**都不得**清空原凭据，也**不得**覆盖更新后的凭据。

## 5. 界面里的恢复入口

| 位置               | 看到什么                                                                  |
| ------------------ | ------------------------------------------------------------------------- |
| 模型选择器         | 按连接的短摘要（如「获取模型列表时地址被本地安全策略拦截」）+「查看连接」 |
| 连接详情           | 短摘要 + 建议动作按钮 + 可展开的长说明                                    |
| 连接详情（管理员） | 部署说明：3.0 / 3.1 / 3.2 的取证与恢复步骤                                |
| 普通用户           | 自己能执行的恢复；看不到部署变量与他人连接                                |

模型选择器里的告警不会挤掉搜索框与模型操作；多个连接同时失败时，每个连接各自可点。

## 6. 已验证案例：三层问题叠在一起（2026-10-28）

同一台服务器上「所有服务商都连不上、连新增的也不行」，实际是**三层独立问题**叠加，
只修其中一层仍然会失败。按下面的顺序逐层取证、逐层验证。

| 层 | 现象                                              | 根因                                                | 判定手段                                     |
| -- | ------------------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| 1  | 目录拉取一律 `address_blocked`（502），**新增的也一样** | 代理的 TUN `dns-hijack: any:53` 把本机**所有** DNS 劫持成 fake-ip | 3.0.1：问任何解析器都得到同一个 `198.18.0.x` |
| 2  | DNS 改成真实 IP 后，某些厂商仍然超时 / TLS 被重置   | 代理组**当前选中的节点**到该厂商不可达              | 3.4：逐节点 `delay` 探测                      |
| 3  | 某条连接报 `token_expired`                          | 登录态真的过期，与网络无关                          | 快照里的 `stage` / `reason` / `upstream_status` |

这一层的关键认识：

- **第 1 层会让「新增供应商」也失败**，因为它拦的是域名解析结果，不是某个连接；
  看到 `address_blocked` 就该去查 DNS，而不是查 Key 或后端代码。
- **第 2 层不会表现为「拦截」而表现为「超时」**，容易被误判成应用 bug；
  它和第 1 层互相独立，**修好 DNS 不等于修好节点**。
- **第 3 层只在第 1、2 层都解决后才会暴露**（之前被网络错误盖住了）。
  遇到 `token_expired` 就重新登录，**不要**去换 Key。

验证顺序：先按 3.1 或 3.2 解除拦截 → 在**容器内**重跑应用自己的出站代码路径 →
确认报的是「凭据被拒」而不是「连不上」→ 再按 3.4 处理节点 → 最后处理第 3 层的登录态。

> 解除拦截后，正确的结果是**厂商真的返回了 401/403**（凭据或权限问题），
> 而不是「超时」。仍然超时，说明卡在第 2 层。

## 7. 仍然待证的事项

以下**必须**由部署责任人或账号所有者在真实环境里完成，不能由自动检查替代：

- 真实 ChatGPT 授权、真实厂商凭据下的推理与额度；
- 放行网段或改成真实 DNS 后，模型调用是否真的成功；
- 重新登录后目录错误是否已清除。

在没有这些证据之前，**不得**宣称「生产根因已定位」或「恢复已生效」。
